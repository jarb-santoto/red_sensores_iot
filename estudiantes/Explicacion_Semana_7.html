1. La Gran Revelación: ¿Para qué construirlo?

Después de seis semanas escribiendo cada nodo y cada enlace a mano, descubrimos que Java ya tiene todo hecho en el Java Collections Framework (JCF). ¿Fue tiempo perdido?

La analogía del Chef: Imagina que quieres aprender a cocinar. Podrías empezar comprando una cocina industrial ya montada con procesadores de alimentos automáticos. Pero el chef que sabe cómo picar la cebolla a mano es el único que entiende por qué un corte es más rápido que otro, o por qué una herramienta se rompe si la fuerzas.

Construir las estructuras a mano no fue para "no usar la biblioteca", sino para desarrollar el ojo clínico. Ahora, cuando eliges entre un ArrayList y un LinkedList, no lo haces porque "está en el libro", sino porque puedes sentir el costo de mover los datos en la memoria.

2. El Mapa del JCF (Interfaces vs Implementaciones)

El JCF funciona con un concepto poderoso: Programar contra la Interfaz.

La analogía del Enchufe: La interfaz es como el enchufe de la pared. No importa si la electricidad viene de paneles solares, una represa o un generador (la implementación); mientras el enchufe tenga la misma forma, tu lámpara funcionará.

En el código, usamos List (el enchufe). Si mañana decidimos que la plataforma necesita cambiar de ArrayList a LinkedList, solo cambiamos una línea del constructor y el resto del sistema ni se entera.

Explicación del código fuente (RepositorioColeccion):

// Definimos que usamos la "forma del enchufe" (List)
// pero el "mecanismo" es un ArrayList
private List<LecturaSensor> lecturas;

public RepositorioColeccion() {
    this.lecturas = new ArrayList<>();
}

¿Por qué es así? Si declaramos el atributo como ArrayList, estamos "casados" con esa herramienta. Al usar List, mantenemos la libertad de cambiar el mecanismo interno sin romper el contrato con el resto de la plataforma.

3. El Secreto del Iterador (for-each)

Descubrimos que recorrer una LinkedList con un ciclo for(i=0...) es la forma más lenta posible de programar.

La analogía del Libro:
Forma lenta (get(i)): Quieres leer la página 10. Abres el libro, cuentas desde la página 1 hasta la 10. Luego quieres la 11, cierras el libro y... ¡vuelves a contar desde la página 1 hasta la 11! Absurdo.

Forma rápida (Iterador): Pones un separador en la página 10. Para leer la siguiente, solo pasas la hoja. El for-each de Java usa un iterador: un separador invisible que recuerda dónde te quedaste.

Explicación del código fuente (Suma Optimizada):

public double sumaPm25() {
    double suma = 0;
    for (LecturaSensor l : lecturas) { // Usa el Iterador (el separador)
        suma += l.getPm25();
    }
    return suma;
}

La diferencia: En lugar de pedirle a la lista "dame la posición 500" (lo que obliga a la lista a contar desde el inicio), el for-each le dice: "dame el siguiente". Es la diferencia entre caminar 500 pasos cada vez o simplemente dar un paso más.

4. Criterios que Viajan (Comparators)

Ya no escribimos un método de ordenamiento diferente para cada campo. Ahora creamos un Comparator.

La analogía del Juez: Imagina que tienes un grupo de atletas. No necesitas contratar a un juez para "correr", otro para "saltar" y otro para "nadar". Contratas a un juez general y le das un Manual de Criterios.

"Para esta prueba, usa el manual de Velocidad". "Para la siguiente, usa el de Resistencia". El algoritmo de ordenamiento es el juez; el Comparator es el manual.

Explicación del código fuente (Encadenamiento):

// Creamos un manual de dos reglas:
Comparator<Alerta> criterio = Comparator.comparingInt(Alerta::getSeveridad).reversed()
                                           .thenComparingLong(Alerta::getOrdenDeLlegada);

Lógica: El método thenComparing es la clave. Le dice al programa: "Si hay un empate en la severidad, no te rindas; abre el manual en la siguiente página y usa el orden de llegada para decidir". Esto hace que el ordenamiento sea estable.

5. Trampas de la Biblioteca

Usar la biblioteca estándar no es mágico; tiene sus propias reglas que, si ignoras, rompen tu programa.

La Trampa del Stack: La clase Stack de Java es antigua y lenta. La recomendación profesional es usar ArrayDeque.

la Trampa del Modificar: Intentar borrar un elemento de una lista mientras la recorres con un for-each lanza una excepción. Es como intentar cambiar las llantas de un auto mientras vas a 100 km/h. La solución es usar un Iterator explícito o el método removeIf().
